reasons behind slow raytracer:

12.6M rays in 23.139s → ~545k rays/sec is indeed very low for primary rays on a CPU. In a JVM ray tracer, that usually means you’re measuring more than “just tracing”, or you’re paying huge overhead per ray (allocations / virtual dispatch / RNG / object-heavy math / I/O).

Here are the most common causes (in roughly the order I’d check), plus fixes.

1) You’re timing I/O (writing the image) or logging

If your timed block includes:

writing PPM/PNG to disk

printing progress per scanline/pixel

building a giant String

…your “rays/sec” becomes meaningless.

Fix
Time only the render loop, not file output:

val (pixels, dur) = measureTimedValue { renderToPixelBuffer(world) }
println("Render: ${dur.inWholeMilliseconds} ms")
saveImage(pixels) // not timed


Also: don’t println() inside hot loops (even once per scanline can hurt).

2) You allocate per ray (or per hit test)

In Kotlin, this is the #1 killer:

creating Ray objects

creating new Vec3 for every add/mul

creating Interval(rayT.min, closestSoFar) in every loop

creating Hit objects for every intersection candidate

GC + allocation churn can easily drop you to sub-1M rays/sec.

Fixes

Make math types allocation-free in hot paths:

use mutable vectors, or

use inline/value classes carefully, or

store components as primitives (Double/Float) and operate with functions.

Avoid creating Interval repeatedly. Pass tMin, tMax as doubles.

Avoid creating a Hit for “miss” candidates; fill a reusable record.

Example change (big win):

// instead of: hit(ray, Interval(tMin, tMax)): Hit?
fun hit(ray: Ray, tMin: Double, tMax: Double, out: HitRecord): Boolean


…and reuse out per ray.

3) Too much polymorphism / virtual calls in the inner loop

If your scene is a List<Hittable> with many object types, you’re doing:

virtual dispatch per object per ray

often multiple allocations per hit

Even with BVH, if traversal calls lots of virtual hit() methods, it can be slow.

Fixes

Ensure BVH is actually used for traversal (world contains only the BVH root).

Minimize polymorphism inside traversal:

store primitives in arrays, or

use sealed classes and when (sometimes helps), or

separate geometry from materials.

4) Your BVH might not be helping (or is broken)

Symptoms:

BVH root exists, but leaf nodes still contain large lists

bad comparator / bounding boxes wrong → lots of missed culling

sorting subList views incorrectly (Kotlin/Java pitfalls) or rebuilding boxes wrong

Quick check
Add counters:

number of bbox tests

number of primitive hit tests

If primitive tests are close to “objects per ray”, BVH isn’t effective.

5) RNG is dominating (especially if you path trace, but can still hurt)

JVM Random can be relatively expensive if called a lot per sample.

Fix
Use a fast per-thread RNG (xorshift/splitmix) or ThreadLocalRandom for Java. For Kotlin/JVM, a simple custom RNG per thread is often a big speedup.

6) Not using all CPU cores

549k rays/sec looks like either:

single-threaded, or

heavily blocked on GC / IO

Fix
Parallelize by scanlines/tiles using a thread pool and per-thread RNG + per-thread temp objects.

7) JIT warmup and measurement method

First run on the JVM can be much slower.

Fix
Run a warmup render (small resolution) before timing the “real” render, or render twice and time the second.

8) Kotlin-specific overhead (data classes, operator overloading)

operator fun plus/minus/times creating new Vec3 instances is convenient but often deadly.

Fix
Replace operator-heavy immutable vectors with:

mutable vector with set/add/mul methods, or

functions operating on primitives.

A quick “why” based on your numbers

23.139s for 12.6M rays means ~1.8 microseconds per ray. On CPU, a primary ray with BVH should often be well under that unless you’re:

allocating several objects per ray, or

doing lots of list iteration / polymorphism, or

timing includes output/logging, or

BVH not actually reducing intersection tests.

Fastest way to know: profile

If you can, use JFR (built-in) or async-profiler:

If you see println, FileOutputStream.write, string building → it’s I/O/logging.

If you see Vec3.<init>, Interval.<init>, Hit.<init> → allocations.

If you see Random.nextDouble dominating → RNG.

If you see ArrayList.get + virtual hit dominating → data layout/polymorphism.
